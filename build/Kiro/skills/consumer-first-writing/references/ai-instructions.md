# AI 指令与配置的文字分层

## 确认实际加载关系，用它分配内容

文件在磁盘上存在，不等于已被加载。根据可核实的宿主行为、配置和任务约定判断谁接收什么；不预设子代理一定看不到历史，也不预设所有规范已继承。下表说明常见位置的阅读任务，不代替实际加载证据。

| 位置 | 实际读者需要什么 |
|---|---|
| 主代理的调度说明 | 如何选择、提供任务、安排依赖与并发、答复澄清、接收和验收 |
| 子代理 description | 是否适用、角色边界、本次应提供的信息、会得到什么可用结果 |
| 子代理 developer_instructions | 自己怎样理解任务、工作、澄清、停止和返回 |
| 当前委托消息 | 当前目标、工程位置、范围、已知证据、约束与验收条件 |
| 结果与报告 | 结论、依据、产物、限制、未决事项 |
| Skill 的名称与描述 | 选择 Skill 的依据 |
| Skill 正文与参考 | 使用者完成当前任务的方法 |
| 机器配置字段 | 宿主实际支持的字段和值，不能靠提示词添加不存在的能力 |

这些关系首先用于作者分配内容。获知“主代理看到 description，子代理另接收执行正文”之后，应让 description 足以支持选择，让执行正文足以支持执行；不把这条投递背景复制成主代理开场的“本节只服务主代理，内部流程在各自配置中”。主代理要调用服务时，这句话没有提供调用决定、必要输入或结果处理动作。若任务是写宿主配置手册，加载机制本身才是需要解释的主题。

当前作者与成稿读者即使都叫 Agent，也有不同任务。要求你消除配置重复，就在配置原问题处完成修改；不要给未来负责工程任务的主代理新增“避免把选择说明和执行细则重复写两遍”的编辑工作。面向写作代理的编辑规范则可以讲这件事，取决于它实际负责什么。

## 沿调用过程核对，而非缩写全部执行规则

审阅时分别找出：调用前必须由主代理提供的动态信息、执行者已有的稳定规则、执行后才生成的结果，以及主代理接收后的动作。

- 不因旧稿把某项列在“请求”里，就认定它是必要输入；需要从实际执行和交接约定核对。
- 执行者自行生成报告并返回位置时，调用者读取实际返回值；不能倒过来要求它先指定执行者的内部命名与保存路径。
- 执行定义已完整包含任务理解、方法、澄清和回传时，保留即可；再加身份、输入、输出概览不会自动提高独立可用性。
- 主代理自检、子代理自证、独立审查与最终验收可以各有阶段和目的。文字优化不授权取消验证、重分职责或新增审批流程。

### 选择说明怎样帮助当前决定

description 的任务是帮助调用者匹配当前问题，并知道怎样开始交接。它不是 developer_instructions 的缩写，也不是把执行者的职业守则改成第三人称再复述一遍。

先从调用者正在考虑的问题写起：我遇到什么情况应选它？当前任务需要交给它哪些材料？得到的结果能支持哪一步？从执行正文取材时，只提取能回答这些问题的信息。

内部的调查顺序、证据审查纪律、假设处理策略、保存办法、输出栏目名，通常留在执行正文。调用者收到“变更、验证结果与未解决事项”就能理解返回内容时，不必再背一串 RESULT、CHANGES 等标题；只有确实需要逐字段解析时才保留字段协议。

边界也按实际误用风险取舍。若角色名称和触发条件已经足以区分任务，无需再逐项声明“不代替谁、不承担什么、不把什么当作什么”。若两种服务确实容易混淆，例如一种仅定位故障而另一种直接修复，边界可以简短写清。重点是防止当前选择错误，不是完整展示执行者的自律要求。

同样，主代理协作说明要给它自己的选择、派发、接收、推进和验收动作。不能把子代理每个工作阶段介绍一遍，视为“教会主代理使用”。在主代理没有选择或操作责任的位置，不留“执行者按自己的规则处理”这类内部过程的替代摘要，直接接上主代理下一项有效动作。

选择角色发生在调用前。子代理已收到任务时，应处理任务和自身边界；“什么时候主代理不要调用我”属于选择说明。调查者可以并行读取材料，不自动意味着它能创建更多调查者。调度数量、共享写入冲突、主线程避免重复劳动由调度者负责。

角色条件真的影响执行时可以说明，例如一份指令确实会被不同角色加载时限定适用行为。适用条件要约束真实行为，而非仅宣告文档服务谁。

### 完整示例：修正调用说明，保留执行能力

这是虚构系统。调用者看到 description 与调用说明；执行者另接收 developer_instructions。任务只要求优化协作文字，不改变检索能力。

原调用说明：

~~~markdown
需要查明本地实现时，向 Tracer 发送项目目录、调查问题和报告目录。
要求 Tracer 先查符号索引，再核对调用方；报告使用“证据、答案、未决项”三段，写入 .local/investigations/result.md。
收到结果后读取报告，依据证据决定下一步；有缺口时补充调查信息。
~~~

原执行配置：

~~~toml
name = "Tracer"
description = "本地实现调查。调用时提供项目目录、调查问题、报告目录。先查索引再核对调用方，使用三段报告。"
developer_instructions = '''
你负责本地实现调查，只读源码。
收到项目目录与调查问题后，先查符号索引，再核对调用方；证据冲突时读取上下文并标明未确认项。
报告使用“证据、答案、未决项”三段，写入当前项目的 .local/investigations/result.md。
完成后向调用方返回实际报告路径、直接答案和缺口。目标或范围不清时，说明影响并请求补充。
'''
~~~

修订后的调用说明：

~~~markdown
需要查明本地实现时，向 Tracer 发送项目目录、调查问题、已知线索和范围限制。
收到结果后按实际回传位置读取报告，依据证据决定下一步；有缺口时补充调查信息。
~~~

修订后的 description：

~~~toml
description = "需要确认本地实现及调用关系时调用。提供项目目录、调查问题、已知线索和范围限制；返回有证据支持的答案、未确认事项及报告位置。仅调查，不修改源码。"
~~~

developer_instructions 保持原样。检索顺序、冲突处理、报告结构、保存规则与澄清行为全部保留。

为什么这样改：

- 调用者提供本次问题，接收结果并决策；实际执行流程没有使用调用者指定的报告目录，因此移除这项伪必填输入。
- 检索步骤与保存规则在执行者处已完整定义，调用者也不依赖其内部目录。去掉调用说明和 description 中的副本就够了。
- 不再补一句“Tracer 会按自己的配置选择步骤、模板和保存路径”。它仍然在介绍同一批内部事项，对调用者没有新增用途。
- 不把内部文件名中的占位符变成新的必填任务参数。执行者会自行命名时，无需让调用者额外提供标题或编号。
- 执行者原文已经交代职责、过程与返回，不需要再加一段相同的身份、输入、输出概览。保持它不变，正是保留用户已有能力。
- 这些结论来自本例的实际加载与使用关系；不是规定所有系统都必须如此。

### 对双方分别写他们自己的动作

调用方可以写：

> 委托时提供目标、范围与现有证据；收到澄清请求后补充缺失事实，涉及未授权范围时取得决定再推进。

执行方可以写：

> 收到任务后判断目标和范围是否足够明确。可从获准材料核实的事实自行核实；关键缺口或冲突会改变结果时，向调用方说明当前理解、缺失信息、影响及需要回答的问题，暂停依赖该信息的工作。收到补充后继续。

两段共同建立交接，各自规定本人的行为。不要把执行方段落改成“调用方必须提供以下字段”，也不要删掉执行方发现问题后主动询问和恢复工作的职责。

语义完整的委托不必因为缺少某个标题就被拒绝。七段式、搜索深度、目录与输出字段只能来自当前系统的真实约定。澄清使用实际可用的消息或返回通道，不能虚构工具，也不能只把问题藏在无人读取的报告里。

## 跨文件验收

分别站在三种接收位置试读：

- 选择者能否凭可见描述选对角色、发送足以开工的任务？
- 执行者能否凭自身规则、当前任务和可访问材料工作、澄清并返回？
- 接收者能否核对结果、证据与未知，继续实际任务？

从调用方移除内部步骤后，核对它自己的任务拆分、依赖安排、结果接收、执行跟踪与验收没有一起被概括掉。执行者仍保留完整工作方法和异常处理。报告路径相对实际任务项目解析，不能把用户级配置的安装位置自动当作产物位置。

出现“不写文件”与“保存报告”等冲突时，核实业务文件与报告文件的边界；不能借文字优化擅改权限。停止一个搜索角度也不等于完成整个调查，整体完成仍应覆盖任务问题。

最后检查原问题所在位置，而不仅是新增的正确说明。真正的修正体现在各自能收到的指令和结果中，不靠另加一段“本次已完成职责分层”来证明。
